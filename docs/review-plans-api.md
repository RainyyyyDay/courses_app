# 考前复习计划（v12）

计划属于固定课程，只保存何时复习哪些内容。实际复习复用现有错题队列和资料／笔记阅读控制器。无 AI、跨课程、知识框架依赖或新的复习步骤。

## 数据与排期

启动自动迁移 v11 → v12，新增 `review_plans`、`review_plan_items`、索引和课程／来源删除约束。旧 migration 保持原样；v12 读取实际 user_version，因此旧版本也能一次启动升级到 v12。不修改旧内容、收藏、review_status 或错题事件。

计划状态为 active / archived。任务状态为 pending / completed / skipped，与内容自身 review_status 完全独立。每个计划内 `(item_type,item_id)` 唯一，不同计划可使用相同内容。

日期必须是真实的 YYYY-MM-DD。包含开始日期，不包含考试日期；考试日期须晚于开始日期。按 type + id 稳定排序，通过累计平均分配，任意两天数量差不超过 1。任务少于天数时存在空白日，不自动移动过期任务。第一版上限为 2000 项、3660 天。

完成率与界面统一为 `round(passed / 有效 total * 100)`；跳过、未通过和待完成都留在有效总数中，只有成功复习增加分子。没有有效任务时固定返回 0%，同时显示各项数量。

来源删除后，数据库仍设置 source_deleted=1 并保留 title_snapshot，供既有复习会话继续识别原身份；该任务立即从有效计划任务、日历、日任务和进度分母中排除，不再计入 total 或 skipped。界面左下角统一显示「成功复习 passed / 有效总数 total」，不要求先点「应用新排期」才更新数字。删除计划级联删除任务；删除课程级联删除计划。删除计划不会删除来源内容。

## API

所有路径前缀为 `/api/courses/:courseId/review-plans`，ID 必须为正整数；课程与计划归属均由服务端校验。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/` | 计划列表及总体、今日统计 |
| GET | `/candidates` | 本课程资料、笔记、错题的选题数据，不读取知识树或标签 |
| POST | `/` | 创建计划，成功返回 201 |
| GET | `/:planId` | 详情、剩余天数、每日和今日统计 |
| GET | `/:planId/items` | 任务，可按 scheduledDate、status 筛选 |
| PATCH | `/:planId` | 仅改 name、status |
| DELETE | `/:planId` | 删除计划及任务 |

创建请求：

```json
{
  "name": "期末考试复习",
  "startDate": "2026-10-16",
  "examDate": "2026-10-28",
  "selectedItems": [
    {"type":"mistake","id":1},
    {"type":"note","id":5},
    {"type":"material","id":8}
  ]
}
```

只接收上述字段。空选择、重复内容、非法日期、同日／倒序日期、不存在或跨课程内容返回 400。服务端重查标题、来源和归属，并重新排期，不接收前端标题、courseId 或排期结果。筛选仅用于形成固定选择集合；后续收藏和复习状态变化不改变任务。

列表／详情在数据库字段外返回 `total`、`completed`、`pending`、`skipped`、`completionRate`、`remainingDays`、`today`、`todayStats`。详情另有 `days` 数组，每天含 date、同样的任务统计和按 mistake/material/note 分组的 types。包含零任务日期。

默认任务列表只返回未删除来源；source_deleted=1 的行保留在数据库中但不再进入当前计划队列。标题使用创建时的 title_snapshot。没有直接修改任务状态的公开 API。

PATCH 示例：`{"name":"期末冲刺","status":"archived"}`。修改日期和范围返回 400，需重新生成计划。归档计划保留任务，但拒绝继续写入计划复习结果。

## 复用原复习接口

原请求正文和响应结构保持不变，只增加可选查询参数 `planItemId`：

- 资料／笔记：`PATCH /api/courses/:courseId/materials或notes/:id/review?planItemId=123`，正文仍为 `{"reviewStatus":"reviewed"}`。
- 错题开始：`POST /api/courses/:courseId/mistakes/:id/review?planItemId=123`。
- 错题动作：`POST /api/courses/:courseId/mistakes/:id/review/events?planItemId=123`。

无参数即普通复习。服务端验证任务所属计划、课程、类型和对象；资料／笔记成功保存 reviewed 才完成任务。跳过和打开不计完成。

错题仍使用原 requestId、expectedVersion 和步骤机，达到 completed 且结果为 reviewed 才完成计划任务；未通过仍保留待完成任务。任务记录实际轮次及内容版本；旧完成结果不能直接抵扣。其他入口已完成同题但计划仍 pending 时，计划会开始实际的新一轮。计划上下文纳入幂等载荷比较，同 requestId 改用另一个任务返回 409；相同请求重试返回首次成功结果。内容和任务更新在原事务内完成，不嵌套 BEGIN。

任务重复完成不会累加数量或覆盖 completed_at。资料／笔记只支持在计划上下文提交 reviewed，不接受 unreviewed。错误继续使用 code/message；归档、已跳过等冲突为 409，任务归属不匹配为 404。

## 前端与恢复

课程 → 复习 → 创建复习计划。搜索、类型、四类错题、收藏和内容状态筛选可组合，隐藏选择保留，全选只影响当前结果。创建前显示数量与每日约数；最终以服务端排期为准。计划创建本身不依赖知识框架，不提供标签筛选；总复习支持现有直接标签筛选。

详情按日展开，支持今日和过期日期补做。一天只显示一张任务卡；进入后所有待复习内容放在同一会话，固定按资料 → 笔记 → 错题排序。无论通过、未通过或跳过，处理完当前项都会自动进入下一项。只有当天全部任务成功时才弹出完成弹窗并播放彩带；存在失败或跳过时只回到当天任务卡，不冒充完成。全部成功时按钮为“再来一次”；存在失败或跳过时按钮为“继续”，只把未成功项带入下一轮。计划创建后只开放改名、归档、恢复、删除。

一天内所有有效任务都已处理（失败也算处理，但跳过不算）且没有跳过时，显示“查看作答”；预览跨该日期的多个复习会话聚合，每题取最后一次结果，因此早先失败、之后重做成功会更新为成功。预览只读，并随打开或刷新重新查询数据库。

阅读复用 createReadingReview 的独立实例和同一界面；错题复用原队列及详情步骤。计划导航键 `review-plan-session:<courseId>`，队列键 `review-plan-queue:<courseId>:<planId>:<date>:<type>`。普通队列、普通错题位置和待确认操作使用原键，互不覆盖。

刷新由计划上下文找到原控制器，仍通过原有恢复逻辑读取队列、重查后端步骤并重试待确认请求。来源删除或任务已完成时从服务端 pending 集合恢复；计划详情进度始终来自后端。页面位置沿用项目现有五分钟恢复有效期。日期统计以 Asia/Shanghai 日历日为准，完成时间使用 ISO 时间。

日期状态固定按当天任务判断：当天有任务且全部成功显示绿色通过；当天尚未全部成功始终显示“今天要复习”，即使部分已通过或跳过；过了当天仍未全部成功显示过期。操作按钮在全通过时固定为“再来一次”，只有存在未成功任务时才显示“继续”。

“应用新排期”只在计划偏差时亮起：过去日期未全部成功、任一未来任务被提前成功复习，或今天/未来仍需复习的内容被删除。普通同日部分完成、按时复习引起的记忆状态变化本身不会要求立刻重排。应用后只替换未来排期快照，不改写已经发生的通过、未通过、跳过和历史日期状态。

计划日提供 `GET /api/courses/:courseId/review-plans/:planId/days/:date/answers`，跨该日期所有计划会话按题目聚合最新一次处理结果，供只读作答预览使用。

日历中的未来轮次可能来自排期快照而不是当天已物化任务。启动这类日期时，服务端按整份计划的来源范围确认内容归属即可；不得因为 `scheduled_date` 没有同日物化行而误报“计划任务不可复习”。

## 固定排期与重新排期（2026-10-24）

普通执行保留已确认的排期快照。当天完成部分或全部任务只更新进度和记忆记录，不重新计算未来安排，也不显示“应用新排期”。在其他入口改变同一内容的记忆评分，同样不会单独触发排期调整。

`GET /api/courses/:courseId/review-plans/:planId/schedule` 的 `hasNewSchedule` 只由以下 `rescheduleReasons` 触发：

- `content_deleted`：计划选中的内容被删除。
- `completed_early`：未来日期中的任务提前成功完成；只完成该日的一部分也算。比较实际完成日和任务安排日，不要求整个未来日期全部完成。
- `overdue`：已跨过安排日期仍有未通过／跳过／未完成的项目，或任务后来才补做完成。当天还未到结束时不算逾期。

日期边界使用 Asia/Shanghai。只打开任务、正常完成当天任务、单纯记忆状态变化不会触发。调整原因会显示在日历上方。查看日历保持原安排，只有用户明确点击“应用新排期”才按当前记忆状态重新计算；应用会确认这次删除／提前完成／逾期事件，避免重复提示。没有待调整事件时重复调用应用接口为无操作。

初始读取建立快照，后续普通读取不运行排期算法。快照元数据仍放在既有 `schedule_json` 字段，不新增数据库迁移；旧快照保持原有日期。复习任务、评分及历史记录保留。

针对性验证：`node --test tests/plan-reschedule-triggers.cjs tests/frontend-script-syntax.cjs`，覆盖固定日期下的部分完成、全部完成、跨天、提前完成部分任务、删除、应用后去重、旧快照、北京时间边界，以及桌面／手机日历交互；仅使用隔离数据库。
